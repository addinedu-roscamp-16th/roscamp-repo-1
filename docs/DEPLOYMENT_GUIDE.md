# FryBot 배포 가이드

이 가이드는 FryBot의 프론트엔드, FastAPI·MySQL, ROS 2 패키지를 공용 환경에 반영할 때 사용합니다. 각 배포에 담당자 한 명을 지정하며, 같은 환경에서는 이전 배포의 종료 공지가 올라온 뒤 다음 배포를 시작합니다. 시각은 팀 채널에서 한국 시간(KST)으로 기록합니다. 환경명과 실행 호스트는 운영 담당자가, GitHub 보호 설정은 저장소 관리자가 확인합니다.

## 배포 원칙

1. `main`에 직접 푸시하지 않습니다. 작업 브랜치에서 PR을 열고 팀원 한 명 이상 승인과 필수 CI 통과 후 병합합니다. GitHub Actions의 필수 검사와 브랜치 보호 적용 여부를 저장소 관리자와 확인합니다.
2. 대상 환경별로 담당자 한 명이 공지·기동·검증·복구·종료 기록을 맡습니다. 프론트와 서버를 서로 다른 담당자가 준비했더라도, 같은 환경에서 반영할 때는 한 배포로 순서를 조율합니다. 시작 직전에 같은 환경의 진행 중 배포를 다시 확인합니다.
3. 배포 전에 팀 채널에 환경, 예정 시각, 변경 내용과 PR 링크, 예상 영향을 알립니다. 공지에 댓글을 달아 배포 시작·진행·종료를 기록합니다.
4. 시작할 때 실제 적용하는 커밋 SHA 또는 이미지·패키지 버전을 기록합니다. 여러 모듈이 바뀌면 웹·서버·DB 스키마·ROS·지도 버전을 각각 적습니다. 배포 전 검증한 버전과 적용할 버전이 같은지 확인합니다.
5. 문제가 생기면 같은 스레드에 영향 범위, 중단 또는 롤백 여부, 다음 상황 공유 예정 시각을 남깁니다. 종료 시 결과와 현재 적용 버전, 핵심 기능 확인 결과를 기록합니다.

## GitHub Actions

`main` 대상 PR과 `main` 푸시에서 Python 문법 검사, 웹 테스트·빌드, API 이미지 빌드를 실행합니다. 웹 소스는 `npm run lint:syntax`로 HTML·CSS·JavaScript·TypeScript 문법을 별도로 검사합니다. `main`에서 검사 통과 후 Actions 실행의 Artifacts에 커밋 SHA별 웹 빌드와 API 이미지 아카이브를 올립니다. 공용 서버 반영은 아래 적용 절차를 따릅니다.

## 배포 전 확인

| 대상 | 시작 전에 확인할 내용 |
|---|---|
| 공통 | PR 승인, 필수 CI 결과, 배포할 버전, 이전에 동작한 버전, 대상 환경과 담당자, 복구 가능 여부 |
| React 웹 | `npm test`와 `npm run build` 결과. 배포용 `dist/`를 생성한 커밋, 직접 연 화면 주소의 SPA 라우팅과 `/api`·WebSocket `/api/ws` 전달 설정 |
| FastAPI | [팀 I/F 목록](https://oneteam1.atlassian.net/wiki/spaces/1/pages/24641549)과 OpenAPI에 맞는 경로·응답·상태 코드. 상태 조회와 WebSocket 연결을 별도로 확인 |
| MySQL | 신규 개발 DB와 기존 스키마에서 마이그레이션 검증. 백업 시점 및 복구 절차, 이전 서버 버전과의 호환 여부 |
| ROS 2·지도 | 패키지 빌드 결과와 시뮬레이션 확인. 변경한 인터페이스와 맵 버전, 실기기에서 진행 중인 임무와 대상 장비 상태 |

## 적용과 검증

1. **적용 대상을 고정합니다.** 배포 목록과 PR을 대조해 모듈별 SHA 또는 이미지·패키지 버전을 기록합니다. 웹·서버·ROS를 같이 검증했다면 그 버전 조합과 지도·스키마 버전도 남깁니다.
2. **의존성 순서대로 반영합니다.** 기존 서버와 호환되는 DB 변경이라면 DB를 먼저 적용하고, 새 인터페이스 제공 모듈을 소비 모듈보다 먼저 준비합니다. 호환이 깨지는 변경은 팀과 적용 순서 및 점검 시간을 합의합니다. 각 단계가 실패하면 다음 단계로 넘어가기 전에 영향과 복구 여부를 확인합니다.
3. **모듈이 켜졌는지 확인합니다.** FastAPI 상태 확인과 DB 스키마 확인, 웹 화면 로드 및 API 연결, ROS 노드·시뮬레이션 응답을 변경 범위에 맞게 점검합니다.
4. **업무 흐름을 확인합니다.** 시뮬레이션에서 **방문 접수 → 주문 등록 → 임무 처리 → 화면 서빙 완료**를 기준으로 확인합니다. 주문을 다시 보냈을 때 중복 등록되는지, 연결이 끊겼다 돌아왔을 때 최신 상태를 다시 읽는지도 관련 변경에서 확인합니다. 실제 영업 주문을 생성하거나 장비가 움직이는 점검은 대상 환경의 운영 담당자와 조율합니다.
5. **결과를 남깁니다.** 실패 또는 롤백을 한 경우에도 복구한 버전과 다시 확인한 기능을 적습니다. 다음 담당자는 종료 공지를 확인한 후 시작합니다.

현재 프론트 목업과 ROS 시뮬레이션은 각각 실행할 수 있습니다. 기존 FastAPI와 ROS 자체 웹의 경로가 React가 기대하는 경로와 달라, 전체 흐름과 공용 환경 자동 배포는 통합 검증이 필요합니다. 배포 호스트, 배포 방식, 실제 환경 이름은 팀 결정에 맞춰 이 가이드에 추가합니다.

## 중단과 복구

- 서버 기동 실패, 명세와 다른 응답, DB 마이그레이션 실패, 로봇 상태 불일치가 확인되면 후속 배포를 멈춥니다. 영향을 받는 화면·장비·주문과 마지막 정상 시점을 기록합니다.
- 웹 배포 파일·서버 이미지·ROS 패키지는 이전에 검증한 버전으로 복구할 수 있는지 확인합니다. 지도나 설정도 변경했다면 호환되는 버전의 조합을 함께 확인합니다. 실기기 변경은 임무를 정리하고 운영 담당자가 상태를 확인한 뒤 적용합니다. 부분 실패가 있으면 장비별 적용 버전과 점검 결과를 남깁니다. [ROS 배포 원문](https://github.com/addinedu-roscamp-16th/roscamp-repo-1/blob/Juheon_Lee/FRYBOT_COMMANDS.md#3-%EC%8B%A4%EA%B8%B0%EA%B8%B0-pinky)
- DB 변경 후에는 이전 서버가 현재 스키마에서 동작하는지 먼저 확인합니다. 호환되지 않으면 다운 마이그레이션이나 검증된 백업 복구의 데이터 영향을 판단해 DB 담당자와 결정합니다.
- 복구 뒤 해당 환경의 현재 버전과 핵심 기능을 다시 확인할 때까지 배포 담당자가 상황 공유를 이어갑니다.
